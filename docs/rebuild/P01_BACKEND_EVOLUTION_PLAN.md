# P01 Backend Evolution Plan

Documented gaps and future backend work discovered or reasoned about during the P01 frontend rebuild. **Nothing in this document is built in this phase.** P01's backend policy was: no major feature development, only the one tiny, additive, backward-compatible fix that was actually required (the CORS origin addition — see `P01_ARCHITECTURE.md`).

## Confirmed content gaps

- **No case-study fields on `Project`.** `overview`, `problem`, `solution`, `outcome`, `challenge`, `development_highlights` do not exist on the backend today. `ProjectCaseStudyFields` in `web/src/lib/api/types.ts` declares them purely for forward-compatibility, and `resolveCaseContent()` (`web/src/lib/case-study-merge.ts`) is already written to give any of these fields precedence over the frontend's own claim register the moment they exist — no frontend change would be needed to light them up.
- **No `services/<slug>/` detail endpoint.** `backend/apps/portfolio/api/urls.py` registers only the list route. The frontend works around this today with a client-side find-by-slug over the full list (only 7 rows), which is a reasonable permanent solution at this data volume — but a real detail endpoint would remove the need to fetch all 7 rows to render 1.
- **No per-project `repository_url` distinct from `github_url`.** Every project except one currently links to the same generic GitHub profile URL (`isDistinctRepoUrl()` in `web/src/lib/format.ts` detects this mechanically). A dedicated field would let a project-specific repository be recorded distinctly from the owner's general profile link without relying on string comparison.
- **`techbuilt-open-school-lms` needs a content owner pass.** This project is published and `featured: true`, but has no `live_url`, no distinct `github_url`, no images, and zero linked technologies, despite marketing language ("production-ready," "scalable") in its own `description`/SEO fields. It was not covered by the original P00 content-truth audit. The frontend deliberately authored no claim-register entry for it (doing so would mean inventing confidence it has no evidence for) — it renders correctly via the plain API-only path, with every empty field rendering honestly as absent. Recommend either completing this project's real data or unpublishing it until it can be verified.
- **No certification model.** `OPEN_DECISIONS.md` #17 records this as still open — no certification exists in the data model, so none is rendered on `/resume` in this phase.

## Roadmapped systems (design intent, not built)

- **Content management.** The claim register (`web/src/content/case-studies/`) is explicitly self-retiring — it exists only to cover the case-study-field gap above. A real CMS or expanded backend model for case-study content would let the register be deleted entirely, section by section, as each field becomes available live.
- **Lead CRM.** `ServiceRequestPayload` already carries `source_page`, so every project-mode contact submission already records which page it came from — the data needed for a lightweight lead-attribution view already flows into the backend today; only the admin-facing view of it doesn't exist yet.
- **Résumé/CV system.** The current résumé view (`/resume`) composes from four separate list endpoints when no `ResumeVersion` is published (see `resolveResumePageState()`), which works but is not the intended steady state — a properly maintained, published `ResumeVersion` row is the better long-term source.
- **Analytics.** `web/src/lib/analytics.ts` is a fully wired no-op abstraction — event names, a sanitizer, a provider-registration seam — with `NEXT_PUBLIC_ANALYTICS_PROVIDER` unset in this phase. Wiring a real, privacy-respecting provider later is a one-line change at the `setAnalyticsProvider()` call site, with zero call-site changes anywhere else in the app.
- **`/ops`.** No internal operations/admin surface exists on the new frontend. Not designed in detail in this phase; noted only as a future need once a CRM view or content-management surface is built.
- **`/insights`.** An engineering-writing section is roadmapped but deliberately not built — no bulk-generated or AI-authored articles were added to reach a content quota. `scripts/smoke-routes.mjs` asserts `/insights` returns a real 404 today, proving this was a deliberate decision rather than an oversight.
- **`SiteSetting.availability`.** A future boolean/enum field on the singleton site-settings model would let a "currently available for new work" signal be database-backed rather than self-declared — until it exists, no availability badge or freelance-availability SEO term is used anywhere on the site (`OPEN_DECISIONS.md` #9).
- **A light/dark theme toggle.** Deferred by design — see `P01_DESIGN_RESEARCH.md`. Would need no backend change, only a persisted client-side preference.
- **CAPTCHA/throttling on the two inquiry endpoints.** Noted as a known gap during the original architecture research (neither endpoint has any request throttling today) — not fixed in this phase, since it is a backend change outside P01's scope. Recommended before any real marketing traffic is sent at `/contact` or `/services/[slug]`.
