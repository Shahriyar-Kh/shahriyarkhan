## Launch blockers

These stop the current site (and any rebuild that assumes it works) from functioning correctly *right now*, independent of any redesign decision.

1. **Live backend database errors.** Every DB-backed endpoint on `https://shahriyarkhan.onrender.com` (site settings, projects, services, skills, résumé, sitemap.xml) returned HTTP 500 when checked on 2026-08-27. **P01A (2026-08-27):** two confirmed code-level crash bugs were found and fixed (résumé default/download-tracking views serializing/dereferencing `None`); a fail-fast startup check was added so a missing `DATABASE_URL`/`POSTGRES_HOST` now fails loudly at boot instead of causing silent per-request 500s. **Still unresolved:** whether the live Render environment's database configuration is actually missing vs. present-but-invalid cannot be determined without Render dashboard/log access — this remains a blocker until an actual deploy + the post-deployment smoke tests in [P01A_STABILIZATION_REPORT.md](P01A_STABILIZATION_REPORT.md) §16 confirm it. See [P00_EVIDENCE_FREEZE.md](P00_EVIDENCE_FREEZE.md) §6.
2. **Live frontend routing failure.** `https://shahriyarkhan.vercel.app` returns HTTP 404 (`X-Vercel-Error: NOT_FOUND`) for every path except `/`, despite `vercel.json` declaring a catch-all SPA rewrite. **P01A (2026-08-27):** root cause found from repository structure alone — `vercel.json` lived at the monorepo root instead of inside the actual Vercel project root (`frontend/`), so Vercel never read it. Relocated to `frontend/vercel.json`. **Still unresolved:** not yet confirmed against a real deployment (see smoke-test checklist).
3. **Canonical domain is undefined.** `frontend/index.html` and its JSON-LD both declare `https://shahriyarkhan.dev` as canonical, but that domain does not resolve at all. The two domains that *are* live (`shahriyarkhan.vercel.app`, `shahriyarkhan.onrender.com`) are platform-default subdomains, not a owned custom domain. **P01A (2026-08-27): a *temporary* canonical was approved and set** (`https://shahriyarkhan.vercel.app`, applied everywhere in public metadata — see "Resolved this phase" above). **Still open:** the *permanent* public domain for the rebuild. Everything downstream — canonical URLs, sitemap, OG tags, email sender domain, JSON-LD — depends on this single answer eventually being made permanent.
4. **Experience-history contradiction.** The home page lists a fourth role ("Python Development Intern," CognoRise InfoTech, Oct–Dec 2024) that does not appear in the résumé page, the backend seed script, or anywhere else — and its dates overlap with another listed internship (Abasyn University Incubation Center, Sep 2024–Feb 2025). **P01A (2026-08-27): hidden from the public site pending verification** (moved to a separate, non-deleted, clearly-labeled constant — see "Resolved this phase" above). **Still open — the underlying question is unchanged:** is CognoRise InfoTech a real, concurrent role that should be added back everywhere once confirmed, or a stale/incorrect entry that should stay removed? This is the owner's own employment history and must not be guessed at.
5. **InsightBoard CRM project status.** Seeded only via a backend management command, using stock Unsplash images as its "screenshots," with a `live_url` that returned HTTP 404 on 2026-08-27. **P01A (2026-08-27): hidden from the public site pending verification** (re-seeded as `status=draft`, excluded from every public endpoint and the sitemap, still fully visible/editable in the Django admin — see "Resolved this phase" above). **Still open — the underlying question is unchanged:** is this a real project that should be documented properly (with real screenshots and a working or clearly-labeled-as-offline demo) and republished, or should it be retired entirely? It must not simply be carried forward as-is, and it must not be un-hidden without first resolving this.

## Technical decisions (owner or engineering-lead input needed, not purely content)

18. **Form-delivery destination and pipeline.** Contact/service-request forms currently send a synchronous email via SMTP or Gmail API to `ADMIN_NOTIFICATION_EMAIL`, with no queue, retry, or CAPTCHA. Decide whether the rebuild keeps direct email, moves to a proper queued/CRM-first pipeline, or both.
19. **Analytics and Search Console access.** No third-party analytics or Search Console integration was found anywhere in the repo — only a self-built `AnalyticsEvent` log, currently unverified against real traffic. Decide whether the rebuild adopts a standard analytics tool, keeps the custom log, or both — and get Search Console access set up against whatever the final canonical domain turns out to be (blocker #3).
20. **Media/storage strategy.** Cloudinary (`django-cloudinary-storage`) and a local disk path (`render.yaml`'s `MEDIA_ROOT=/var/data/media`) are both configured simultaneously; it is not verifiable from the repo which one is actually serving current production media. Needs a decision (or at minimum, verification of current production behavior) before the rebuild designs its media pipeline.
21. **Package-manager standardization (frontend).** `bun.lockb`, `package-lock.json`, and a manual `npm-requirements.txt` all coexist for the same `frontend/` project. Pick one.
22. **Python dependency source of truth (backend).** Root `requirements.txt` (delegating to `backend/requirements.txt`, Django ≥5.2) and `backend/requirements/base.txt` (Django ≥5.1, the one Render's build actually installs via `prod.txt`) disagree. Pick one canonical requirements path and Django version floor.
23. **Hosting and deployment ownership.** Confirm who has access to the Render and Vercel dashboards (needed to actually fix blockers #1–2, and to point them at a real domain per blocker #3) — this audit has no platform access and could not confirm ownership/billing/DNS control from the repository alone.
24. **Privacy/retention requirements.** No `/privacy` page exists today, and no data-retention policy for `ContactMessage`/`ServiceRequest`/`AnalyticsEvent` records was found anywhere in the repo. Needs an explicit decision before a `/privacy` route (in the proposed future IA) can be written truthfully rather than boilerplate.
25. **Testimonials and attribution permission.** None exist today (confirmed absence, not an oversight in this audit). If the rebuild wants testimonials, each one needs to be sourced from a real client/collaborator with explicit permission to quote and attribute them — none may be invented.
